Security & threat model

What the agent can touch, what it can't, and who says yes.

Last updated: 1 October 2026

The threat model assumes the agent is adversarial: the model can be prompt-injected, hallucinate, or loop. So it doesn't get to be trusted. Cashmaxx runs two processes: the agent, which thinks and acts, and the guard, a separate program that holds every credential and makes every spend decision. The agent's only money power is asking. Everything on this page describes what the code enforces, not what the model is told.

The key separation

The guard process exclusively holds the wallet credentials (Coinbase Developer Platform server wallet), the Stripe restricted key, the OpenRouter key, the guard's own Telegram bot token, the owner PIN hash, and any email, social, or hosting credentials you connect. They live in ~/.cashmaxx/guard.json, written mode 0600, read only by the guard.

The agent process gets one thing: an agent token. That token can read state (balance, ledger, settings without secrets) and request spending. It is stored on the guard side only as a SHA-256 digest and compared in constant time. With the agent token you cannot approve an approval, change a rule, or unfreeze — those endpoints require the owner scope, which the agent never possesses.

That means the agent never sees, and therefore can never leak, your wallet keys, your payment credentials, your email password or app tokens, or your social account credentials. A fully compromised agent can at most send well-formed requests — which then meet the policy engine below.

The owner authenticates to the guard directly, with a PIN the agent never sees (stored only as a scrypt hash). Owner sessions are opaque tokens kept in the guard's memory, valid 12 hours, rate-limited, and gone on restart. The guard's Telegram bot uses a different bot token from the agent's chat bot and only acts on messages from your own chat id.

What the agent can do

  • Check its balance and remaining budget.
  • Request a payment: USDC on Base, or an x402 pay-per-call request capped at a stated max_usd.
  • Read the P&L ledger, and record agent-reported costs (clearly marked as unverified).
  • Create a Stripe product and payment link, using the guard's restricted key.
  • Ask for capped outbound work — email sends and social posts — which the guard performs with its own credentials and its own daily caps.
  • Freeze everything. The kill switch is always safe to pull, so the agent can trigger it too.

What the agent can never do

  • Approve its own payment, or approve anything at all.
  • Change budget, caps, thresholds, the allowlist, or any other rule.
  • Unfreeze. Only the owner scope can, via your PIN or the guard's Telegram bot.
  • Make a swap or an arbitrary contract call. The policy engine only knows two spend kinds — USDC transfer and x402 — and rejects everything else. This is hard-coded, not a prompt.
  • Read the guard's config, database, or process memory. Run the guard as a different OS user or container and this is an OS boundary; the agent's shell additionally runs inside an OS sandbox (Seatbelt on macOS, bubblewrap on Linux).
  • Pay twice by retrying. Every payment carries an idempotency key; a replayed request returns the original result.

What triggers an approval

Every spend request runs through the same fixed-order policy. First match wins:

  • Deny outright — if the wallet is frozen; the amount or address is invalid; the spend isn't a plain USDC transfer or x402 payment; it exceeds the available budget; it would break the daily cap; or too many payments went out in the last hour.
  • Wait for you — if the amount is over your per-payment approval threshold, or the recipient is new (not previously paid and not on your allowlist).
  • Allow — everything else: small, in-budget payments to known recipients.

Approvals reach you through the guard's own Telegram bot or the WebUI — channels the agent doesn't control. When you approve, the guard re-checks the hard limits (freeze, budget, daily cap, rate) at execution time, so an approval granted hours ago can't slip through after conditions changed. Unanswered approvals expire after 24 hours. If the guard is unreachable, the wallet tools fail closed: the agent spends nothing.

What the freeze does

Freeze is the first check in the policy engine: while frozen, every spend request is denied, full stop — no amount, no recipient, no exceptions. Anyone can pull it: the Freeze button in the WebUI, /freeze to the guard's Telegram bot, cashmaxx freeze on the CLI, or the agent's own cashmaxx_freeze tool. Unfreezing requires the owner scope: your PIN, or you, in your own Telegram chat with the guard bot.

There is also an automatic one. If you enable the loss stop and your 7-day net P&L falls below your loss threshold, the guard freezes itself and tells you why.

What this is not

Custodial services advertise insurance and screening — a $10,000 protection guarantee here, KYT transaction screening and hardware-isolated keys there. Cashmaxx is the opposite trade: no company holds your keys, so there is nothing to insure and nothing to breach on our side, because there is no "our side." You get a boundary you can read (the architecture and policy engine are in the open) and you accept the responsibilities of running it yourself.

So keep the honest limits in view:

  • The guard protects spending, not the rest of your machine. The agent still has a real shell, browser, and file system — inside its sandbox and workspace, and those boundaries are enforced by your OS configuration, so run the guard as a separate user or container before funding a real wallet.
  • You approve payments over your threshold with a PIN typed by you. If your own machine is compromised at the OS level, no software boundary inside it holds.
  • Blockchain transactions are irreversible. A payment you approve goes out; nobody can reverse it.
  • The guard binds to 127.0.0.1 by default — it listens only on your own machine.

Reporting a vulnerability

Please don't file public issues for security problems. Use GitHub's private security advisory on the repository's Security tab or email cashmaxx@neu.so. More on the support page.
